# International Search and About Profiles

## Publish the Static Update First

1. In GitHub Desktop, open `ashtonmilton` on `main` and click **Push origin** after reviewing the commit.
2. In [GitHub Actions](https://github.com/ashtonmilton/ashtonmilton.github.io/actions), wait for the Pages build and deploy to succeed. The existing workflow builds Eleventy, validates the generated site and tests the dormant Worker separately.
3. Open `/about/`, `/zh/about/`, `/th/about/` and `/ja/about/` directly on the public domain. Check the research and work links, English fallback and page source. Run `python3 scripts/audit-live.py` to check the deployed sitemap URLs, headers and directives from your connection.
4. The three translations use the English profile as their factual source. Update all four when a role, date or affiliation changes. A fluent local reviewer can also check idiom before release.

## Search Consoles

1. **Google:** Open [Search Console](https://search.google.com/search-console). Use the existing verified Domain property for `ashtonmilton.net`; if verification is missing, add a Domain property and publish Google's exact TXT value at `@` in the authoritative DNS provider, without removing existing records. Select **Sitemaps**, submit `https://ashtonmilton.net/sitemap.xml`, then inspect the four About URLs individually. Run **Test Live URL** and request indexing where offered. Measure results in **Performance → Search results**, filtering by page and country. Compare both name queries, and keep Web and Image results separate.
2. **Bing:** Open [Bing Webmaster Tools](https://www.bing.com/webmasters/). Import the verified Search Console property or use Bing's dashboard-provided ownership challenge. Submit the same sitemap under **Sitemaps**. Under [URL Inspection](https://www.bing.com/webmasters/help/url-inspection-55a30305), inspect the exact URL from the warning, its indexed/crawl view and **Live URL**. A warning for the 404 template is expected; a warning for a public 200 page needs the URL, crawl date and captured header/HTML evidence. Test all four profiles. Manual submission is sufficient at this publishing volume.
3. **IndexNow (optional):** Follow the [IndexNow protocol](https://www.indexnow.org/documentation). Generate a key, publish a root-level file named `KEY.txt` containing only that key (add an exact passthrough entry in `.eleventy.js`), and verify its public URL returns 200 before submitting changed URLs. Do not add recurring submissions or secrets until the public setup is tested. IndexNow does not submit to Google.
4. **Baidu:** Sign in to [百度搜索资源平台](https://ziyuan.baidu.com/), add the HTTPS apex under site management, and follow the proof method actually offered. For file verification, put Baidu's supplied file at the public root using an exact Eleventy passthrough, deploy and check its direct URL before clicking Verify. For HTML-tag verification, use the exact dashboard-supplied tag in the homepage head, deploy, then verify. Under [普通收录](https://ziyuan.baidu.com/linksubmit/index), submit the sitemap if that option is enabled for the verified site, otherwise use manual URL submission if offered. Check 抓取诊断 (crawl diagnosis) for the homepage and Chinese profile. Availability and quotas are account-specific; do not assume verification or submission succeeded.

Submission does not establish indexing. Use the consoles' index reports before drawing conclusions about rankings or impressions.

## Optional Country Routing: Approval Required

GitHub Pages only serves the static pages. The Worker in `edge/about-localisation.mjs` is not deployed by GitHub Actions. It uses Cloudflare's IP-country field, not GPS, a browser API, an IP log or a third-party tracking script. VPNs can produce the wrong country; the English link uses `/about/?lang=en` and bypasses routing. JSON-LD, hrefs and canonical URLs do not vary by requester.

Google [recommends against automatic language redirects](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites). The static release is the safest default. If enabled as requested, an English canonical can nevertheless redirect for a requester from CN, TH or JP. Test for that search trade-off. If it is unacceptable, restrict routing to an opt-in navigation entry URL instead and leave clean `/about/` invariant. Never make exceptions based on bot identity.

1. After explicit approval, add the zone to Cloudflare but do not change nameservers until you have copied and checked **all** authoritative records, including email, verification TXT, CAA and DNSSEC status. Retain the registrar and the GitHub Pages origin. Follow Cloudflare's [full setup](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/). Preserve a DNS export and rollback plan.
2. Verify GitHub Pages' custom-domain HTTPS independently. After nameserver migration, test DNS-only first. When enabling proxy for the apex, use [Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/) and verify both client and origin certificates; do not use Flexible mode. Check the apex and www redirects, GitHub's custom-domain status and certificate renewal before proceeding. Keep GitHub's HTTPS enforcement.
3. Deploy the Worker separately and add only the [route](https://developers.cloudflare.com/workers/configuration/routing/routes/) `ashtonmilton.net/about/*` to the proxied hostname. The code additionally checks the exact `/about/` path. Leave the `ABOUT_LOCALISATION` variable unset for pass-through while verifying origin access. Disable Worker invocation logs if not needed. Do not configure edge caching for redirects or ignore query strings on this route.
4. Once the origin and translated pages pass staging checks, set `ABOUT_LOCALISATION=on`. Test CN, TH and JP for a single 302 and GB, US, FR and unknown for English. Test explicit translations, the English fallback, assets and the homepage from those locations. Recheck crawler reports. For rollback, remove the route or unset the variable; the static profiles remain available.
5. Review the [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and [pricing](https://developers.cloudflare.com/workers/platform/pricing/) before activation. This small route is designed for the Free tier if traffic is within its quota. Standard Cloudflare proxying is not the separate mainland China network.

## Mainland China Verification

No mainland vantage point was used in the development audit. Neither UK-based HTTP checks nor user-agent substitution establish regional or genuine Baiduspider access. Test without VPN from at least two mainland access networks, preferably both fixed and mobile, in Shanghai and another location. Record carrier, time, DNS A/AAAA answers, HTTPS certificate validation, any redirects, status, transfer timing and whether CSS, fonts, photographs and the four profiles render. Repeat at different times. The site loads its core assets from its own domain; the external LinkedIn link is not a rendering dependency.

Keep GitHub Pages unless the tests show a repeatable problem. If it is unstable, stage the same build on a Hong Kong and a Singapore static host, compare actual mainland timings, reliability and certificate handling, then price storage, requests and transfer before proposing a move. Hong Kong may offer shorter routes; Singapore is a useful comparison, not a guarantee. Neither bypasses mainland network restrictions. Mainland hosting/CDN distribution is a separate regulatory decision; for example, [Cloudflare's China Network](https://developers.cloudflare.com/china-network/get-started/) requires Enterprise, a separate subscription and ICP documentation. No hosting or network changes are required for the static profiles.
