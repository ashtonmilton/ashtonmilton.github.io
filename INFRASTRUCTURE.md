# Website Infrastructure and Operations

## Architecture

Squarespace remains the registrar, Cloudflare provides authoritative DNS and proxies the apex, and the GitHub Pages workflow builds and serves the public Eleventy output. The public site has no database, mail collector, newsletter database, backend search or private admin assets. Search is a small same-origin index built from listed public HTML after Eleventy runs. The optional public Worker handles homepage language routing and response headers. The dashboard is a separate Worker with a private publishing form that never builds into GitHub Pages.

## Static Release

Run `pnpm install --frozen-lockfile`, `pnpm run build`, `python3 scripts/verify-site.py` and `node --test edge/about-localisation.test.mjs edge/admin/dashboard.test.mjs scripts/publications.test.cjs`. Push to `main` and wait for Deploy Eleventy site to GitHub Pages to finish. Open Work and test its inline search before activating dependent services. Privacy controls are in the footer. The public health script checks canonical URLs and robots directives under four user agents; this is not a fetch from Google, Bing or Baidu infrastructure.

## Cloudflare Activation Sequence

1. Compare DNS records with an export. Confirm both hostnames and GitHub Pages' custom-domain HTTPS. In Cloudflare **SSL/TLS → Overview**, verify **Full (strict)**, then check the apex and www in a browser. Do not infer origin encryption from a public TLS check. In **Edge Certificates**, leave HTTPS enforcement in place. Do not enable HSTS preload.
2. In **DNS → Settings**, review DNSSEC. If it is not active, enable Cloudflare DNSSEC, take the DS data Cloudflare supplies and enter it in Squarespace if supported. Verify the parent DS and an end-to-end validating answer before calling it enabled. Roll back by removing the registrar DS and allowing it to expire before disabling signing at Cloudflare; reversing that order can break resolution.
3. Use the Cloudflare Free Managed Ruleset where available. Observe Security Events before tightening rules. Do not add broad rules that challenge overseas networks, accessibility clients or search crawlers. Leave aggressive bot modes off until verified. The public site has no POST or form API to rate-limit. Keep the optional free rate-limit rule for proven abuse on specific paths. Verify default DDoS and security settings in the account rather than interpreting a header as proof.
4. Deploy `npx wrangler deploy --config edge/wrangler.toml` while authenticated. Add the zone route described in [International](INTERNATIONAL.md). Leave `ABOUT_LOCALISATION` and `SECURITY_HEADERS` off while verifying pass-through; enable and verify the two separately. Test policy/CSP in browser dev tools with the homepage, form, photo controls, responsive images and consented analytics. Disable Cloudflare Rocket Loader, automatic Web Analytics injection and email obfuscation if enabled and incompatible with the CSP; do not enable broad exceptions or inline scripts to compensate. No security settings were changed solely by pushing this repo.
5. Run geographic tests from actual CN, JP and TH networks in addition to simulated unit tests, then test Viet Nam, a default English location, an explicitly selected language and shared article links. A bare homepage URL does not reveal whether it was shared, and URL fragments never reach the server. Query-bearing homepage links, all deep links and explicit language destinations skip auto-redirects. `/?lang=en` bypasses routing even without cookies. Manual language links can set one non-identifying cookie for 180 days. Never base rules on bot user agents.
6. Review **Rules → Cache Rules** and **Speed → Optimization**. Keep origin cache settings or modest asset TTLs for `/assets/`; do not cache everything or force-cache homepage HTML, geo redirects, preference responses, admin content or the search index. Keep compression negotiated; check Brotli with a GET using `Accept-Encoding: br`. Prefer new asset URLs or version queries when changing assets. Purge specific URLs only if necessary. Test both proxied and origin behaviour after changes.

## Analytics and Privacy

Configure a free Cloudflare Web Analytics site for the apex, use the manual JavaScript token as the GitHub Actions **repository variable** `CLOUDFLARE_WEB_ANALYTICS_TOKEN`, and redeploy. This is a public beacon site token, not a Cloudflare API credential. Do not use Cloudflare's automatic injection at the same time. The site does not load the beacon before a visitor selects **Allow Analytics** in the Privacy footer; the same control allows withdrawal. Keep it disabled until the site owner confirms the privacy notice, purposes, processor terms, retention, and handling of IP/network data. This is a technical consent mechanism, not a legal-compliance certification. See the [ICO guidance](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/).

Browser analytics measures only the consenting, observable sample. Cloudflare's [visits and page views](https://developers.cloudflare.com/web-analytics/data-metrics/high-level-metrics/) are not a verified count of distinct people. Use the dashboard's available date, source/referrer, path, country, device, browser and Core Web Vitals views; search referrals can be identified where referrers are present. Use paths for photo essays and language editions. Annual trends require sufficient retention or a separate approved aggregate export; they are not created here. Returning people are not measured because the site does not fingerprint or track identities. Cloudflare edge request counts are distinct from those browser measures and may include bots and sampling. Private analytics tokens must never go in GitHub repository variables or public HTML.

### Readership in the Admin Dashboard

1. Analytics Engine has been enabled for this account. Review the [limits and pricing](https://developers.cloudflare.com/analytics/analytics-engine/pricing/) and the footer disclosure before enabling event collection. The ordinary `edge/wrangler.toml` does not require Analytics Engine and does not collect events. The optional `edge/wrangler.readership.toml` connects the dataset and accepts validated opt-in events. Upload it with `pnpm dlx wrangler@4.168.0 versions upload --config edge/wrangler.readership.toml`, then deploy the version using `wrangler versions deploy` without changing triggers.
2. With `READERSHIP_CONSENT_FALLBACK=on`, the Worker places the analytics switch next to Privacy and serves a private, non-cacheable browser policy based on Cloudflare country detection. Excluded pages and builds marked `READERSHIP_ENABLED=off` remain excluded. `READERSHIP_UK_DEFAULT=on` enables basic first-party page, publication-click and download aggregates for UK connections. Other or unknown regions require opt-in. Explicit opt-outs and privacy signals override the default. Turning the switch on enables basic collection; existing explicit permission for broad search topics and the separate Cloudflare Web Analytics beacon is not broadened and is cleared by switching off. Keep automatic beacon injection disabled and review the [ICO statistical purposes exception](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/what-are-the-exceptions/) when changing collection or processors. Set `READERSHIP_UK_DEFAULT=off` to revert to opt-in everywhere without disabling readership.
3. The admin Worker uses the [Analytics SQL binding](https://developers.cloudflare.com/analytics/sql-api/workers-binding/) to read the dataset. No new token is needed when this binding is installed. For an older deployment without the binding, the fallback requires an account-scoped read-only `READERSHIP_READ_TOKEN` secret and `CF_ACCOUNT_ID` on the admin Worker. Never use the Global API Key.
4. Confirm a fresh UK browser records a view, and that turning analytics off prevents further events. Verify a fresh non-UK browser remains off until opt-in. Inspect the signed-in dashboard once data becomes available. Optional search topics are recorded on Enter or a result click, rather than each keystroke; topics with fewer than three estimated events are not displayed. No raw queries, full referrer URLs, IP addresses or user IDs are stored in this dataset. It does not report distinct readers, reading duration or individual journeys. Use Google Search Console for queries made on Google.
5. To stop ingestion immediately, set the public Worker's `READERSHIP_ENABLED` to `off`. Turn off the GitHub variable and rebuild to remove the controls when no other analytics is configured. Removing the admin SQL binding (or its fallback token) only disables reporting and does not erase the dataset.

## Private Administration and Publishing

### Sign In on the Website

The admin Worker supports its own password form at `https://admin.ashtonmilton.net/`. Cloudflare Access can remain in place while preparing the change; without a native password configured, the previous Access mode remains in use. Do not enable a bypass policy. Never use a Cloudflare or GitHub password as the site password.

1. Deploy the updated admin Worker in a way that preserves its existing Custom Domain, bindings and secrets. The current Wrangler file includes the required `ADMIN_LOGIN_LIMIT` binding. Do not enable `workers.dev` or previews.
2. In Terminal, run `openssl rand -hex 32`. Store the resulting 64 characters in a password manager as the separate site admin password. In **Workers & Pages → ashtonmilton-admin → Settings → Variables and Secrets**, add its exact value as the **Production Secret** `ADMIN_LOGIN_KEY`. Do not paste it into chat or commit it. Deploy the binding.
3. Verify that the site’s own password form works behind the existing Access sign-in before removing the outer sign-in. Then remove only the Access protection for `admin.ashtonmilton.net` and, if present, the Worker-level protection for `ashtonmilton-admin`. A hostname policy takes precedence over a Worker policy, so both may apply in succession. Leave other apps, shared policies, account-wide rules, and DNS untouched. If broader account protection still applies, review it before making any further change.
4. In a fresh browser window, verify that the native password form appears, incorrect credentials cannot enter and the correct password opens the dashboard. Test publishing and reviewing a real approved piece with the repository connection described below. The eight-hour session is host-only, HTTPS-only and inaccessible to JavaScript. Signing out clears the browser cookie; rotating `ADMIN_LOGIN_KEY` invalidates all outstanding sessions. Cloudflare rate limits sign-in attempts approximately per IP and location. There is no password-reset email or additional login factor; use the Cloudflare Worker settings to rotate a lost password.
5. To revert, restore Access for the admin hostname **before** removing the native login secret or rolling back the Worker. To disable write access independently, remove `GITHUB_PUBLISH_TOKEN`.

**Work** edits new and existing articles, notes and photo essays at their original URLs. **Pages** covers the English pages, 404 copy and every existing translated profile; generated profiles edit only that language's entries, not templates, locale IDs, institutional facts shared between editions or routing. **Upload a Public File** is a separate, immediate public release for approved PDFs and images (up to 4 MiB); it does not create a catalogue entry. Use **Upload Private Images** in a photo essay for work in progress.

**Private Drafts** uses the `EDITORIAL_DB` D1 binding on the admin Worker only. The owner can sign in on another device and restore saved drafts; draft revisions prevent one session from silently replacing a save from another. Saving or discarding a draft and uploading private images do not write to GitHub. **Publish Selected Pages** releases up to 10 page drafts in one commit. Publishing a photo essay with private images puts the essay and its new images into one commit, after checking the source revision. Publication of a single Work item still triggers one site build. The private photo pool is capped at 48 images of up to 4 MiB each; unused images can be removed in Drafts. Local text backups do not include file attachments.

Initialise an empty replacement database with `pnpm dlx wrangler@4.168.0 d1 execute ashtonmilton-editorial --remote --file edge/admin/editorial-schema.sql --config edge/admin/wrangler.toml`. Preserve the existing D1 ID and admin secrets on subsequent deployments. Git covers released content and assets only; keep any D1 export private and use it to restore unreleased material. Rolling back the Worker version does not remove stored drafts or alter the public site.

**Edit Work** lists articles, notes, academic pieces and photo essays together, regardless of when they were added. Older formatted articles open in the same Markdown editor; an unchanged body is preserved when you only update metadata. **Pages** handles headings, text and direct link destinations on the main pages and the standalone Chinese, Japanese, Thai and Vietnamese profiles. The remaining regional profiles still use the shared localisation source files.

The **Related Work** checkboxes are available when creating or editing articles, notes and photo essays. Existing selections are preselected, including existing research or policy links. Checked links are saved in `relatedReading` and displayed at the end of the public piece. Clearing all selections uses the public page's tag-based suggestions, rather than saving links to fixed targets. Generated suggestions update when work is unpublished and do not prevent removal.

**Featured Work** lets you order three published items without changing the homepage layout. The photo editor, for both old and new essays, shows previews, lets you upload images in the same window, and keeps each caption, alt text, location and note attached when you move the photo. Use drag handles or the up and down buttons. Photos may share a two-image spread. The first photo is the social preview; keep each essay between two and 12 images. Removing a photograph from an essay leaves the image file available in **Public Files**.

**Unpublish** removes a piece from the public site, Work, search, sitemap and feed after deployment. The admin retains it for restoration at its original URL. Remove featured selections or incoming links before unpublishing a linked piece. **Public Files → Remove File** removes an unused upload in a reversible Git commit. Both operations use the reference index when it matches the current branch, or check the exact GitHub source revision when the index is missing or stale. No changes are made if the check cannot be completed or if the branch moves. No history is rewritten: do not treat removal as an erasure from earlier public commits or copies.

### Connect Publishing

1. Confirm the Work update is published and the admin Worker is deployed. Create the Access application and exact-email policy first; add `ACCESS_AUDIENCE` and `ADMIN_EMAILS` on the Worker, then attach the custom domain `admin.ashtonmilton.net`. Test anonymously and signed in. A wrong or missing identity must not reach the dashboard.
2. In GitHub, create a fine-grained personal access token scoped to the one `ashtonmilton.github.io` repository, with repository **Contents: Read and write** and no other optional write permissions. Use an expiry and rotate it when needed. [GitHub documentation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)
3. From the repository, run `pnpm dlx wrangler@4.168.0 secret put GITHUB_PUBLISH_TOKEN --config edge/admin/wrangler.toml` and enter the token into Wrangler’s interactive prompt; never place its value in the command, the repository or chat. This secret belongs only to the admin Worker.
4. Sign in and use **Publish Work**. Supply a title and summary, pick the type, then paste Markdown or upload a UTF-8 `.md` or `.txt` file (maximum 100 KiB). Add tags if useful. Confirm public release and submit. The Worker creates a new file under `src/writing/essays/` on `main`; the existing Pages workflow updates the article, Work archive, search index, sitemap and dated feed. The receipt distinguishes a commit from a successful deployment.
5. Verify with a real piece you have approved. Creating a publication refuses existing URLs; edits use the revision-aware Work editor. There is no PDF or Word conversion. Use GitHub Desktop for source rollback. Removing `GITHUB_PUBLISH_TOKEN` disables GitHub writes without deleting private drafts or read-only dashboard data. Revoke it in GitHub if it is ever exposed.

## Publications and Backups

Keep unpublished material out of the **public Git repository**, not merely out of the generated site. For an explicitly approved release, put the final file below `publications/files/` and add a record to `publications/catalogue.json` with `release: "public"`, stable lowercase `id`, `title`, `description`, ISO `date`, `author: "Ashton Milton"`, `type`, `subjects`, `keywords`, `version`, `citation` and a basename-only `file`. Credit co-authors faithfully in the citation; a different author model needs a schema change. Use a new stable versioned filename when changing a file. The build validates metadata, rejects path traversal, permits only the approved file types and publishes the recorded checksum. No documents were added without approval. No download counts are inferred from the catalogue.

GitHub-backed storage is sufficient for small public files; keep original archival photographs separately backed up. [R2 Standard](https://developers.cloudflare.com/r2/pricing/) can serve larger public assets later, but activation enrolls the account in usage-based billing; leave it off until explicitly approved. Back up the source and approved assets with Git, export private drafts separately when needed, download a DNS export before DNS changes, record nonsecret Worker settings, and back up mail through its existing provider. Do not copy credentials into backups or the repository. Email remains an existing mailto link; no Cloudflare Email Routing, newsletter service or contact form has been added.

## Monitoring, Limits and Rollback

The Pages build checks internal links, metadata, canonical and language links, image files and sizes, and publication releases. A separate GitHub workflow checks live pages, HTTPS/certificate expiry and references after deployment and weekly. Repeated external 404/410 responses fail; publisher 403s, 429s and timeouts are marked for manual follow-up. Lighthouse reports are stored as short-lived GitHub artifacts; its budgets warn during initial baselining. Lab LCP and CLS are not field Core Web Vitals. No real-mainland vantage point or engine indexing status is provided by these tests; follow [International](INTERNATIONAL.md).

The design requires no new paid services. Cloudflare [Workers Free](https://developers.cloudflare.com/workers/platform/limits/) has a shared 100,000 requests/day limit; a wildcard zone route includes assets and other proxied requests. Monitor total usage and keep public pass-through available if the account allows. Web Analytics is free; consult Access seat limits before enabling users and do not accept a paid plan. Existing registrar fees remain. No R2, Argo, paid Workers, paid WAF, paid analytics or paid CI service is needed. Do not assume the owner's currently selected plan until the account is inspected.

Rollback the static release with Git revert and a new Pages deployment. Turn off the optional edge flags or remove the public Worker route for immediate edge rollback; retain valid TLS. Remove the beacon repository variable and redeploy to stop loading analytics. Purge only affected HTML or assets after verifying rollbacks. Never delete public DNS, MX records or the GitHub Pages association as a rollback for an application change.
